**The dev node in a Web Worker, both ways.** With the keys on the MAIN thread: `wrapDevNode(await createWorkerNode({worker, initialBalances: devAccountBalances({accounts})}), {accounts})` runs the EVM in the worker and answers the accounts, sends and signatures on the main thread. With the keys IN the worker: the new `@webevm/devnode/worker-host` entry exports `exposeDevNode({createEngine, accounts, balance, fund, fundAccounts, impersonation})`, the whole of a worker module; it hands webevm's worker host a node factory, so each `createWorkerNode()` (webevm's own client, unchanged) creates a dev node funded at genesis inside the worker, every `SlimNode` member crosses the boundary through webevm's single proxy, an `RpcError` the layer raises (`4100`, `-32602`) reaches the main thread with its `code`, and no key or mnemonic is ever sent to the main thread. The main thread's options (its `initialBalances` included, which still win over the dev funding) pass through as for any worker node. A bad mnemonic, key, count or `balance` never throws at module scope: it is logged in the worker at once and `createWorkerNode()` rejects with the same message, never a hang. `createDevNodeWorkerApi(options)` returns the same api without exposing it. `comlink` is an optional peer dependency (needed only for `/worker-host`, as in webevm). **The `webevm` peer minimum is now `>=0.10.0`**, the release whose `exposeNode` takes a node factory: on an older webevm that option would be ignored silently and the worker would run a plain node with no dev accounts. The README documents both recipes, including that a main-thread layer over a worker proxy serves its ports from the main thread (giving up `serveOn`'s worker-to-worker path) while the in-worker one keeps it.
