# Decisions taken while building state-history-persistence

2026-09-28. In-scope choices made by task `state-history-persistence` that a reviewer may want to ratify or reverse. The architecture (an undo log over the flat state) is ADR 0013, whose "a loaded dump is a baseline until `state-history-persistence`" consequence is updated in place to say the log is now persisted; no new ADR, because the choices below are local to the dump format and have one code site each. Sites are in `packages/webevm/src/node.ts` unless stated.

1. **The open record is FOLDED into the head's record in the dump**, older entry winning, rather than dumped as a separate field. `loadState` clears the open record (the task requires it), so writes since the head (`evm_set*` cheats, a batch that threw mid-block) become part of the loaded head, which reads them live exactly as before the dump; folding keeps their PRIOR values for every read below the head, and the per-key earliest-wins union over `undo[K+1] .. undo[head]` + open is unchanged for every K below the head (proof in the JSDoc). Alternatives: a separate `open` field restored as the open record (would attribute pre-reload writes to the next mined block, and a second new field); dropping the open record (silently wrong answers below the head after a reload, which the round-trip test catches: 30 mismatches with the fold disabled). With no record for the head (history starts at the head) the open record is dropped with nothing lost. Site: `dumpHistory`.
2. **`loadState` restores only the CONTIGUOUS run of records ending at the dump's head**, stopping at the first gap and at the loading node's window, and silently drops anything older. A dump this code writes has no gap; the rule exists so a hand-edited or foreign dump cannot make a read below a gap answer from a later state. Alternatives: trust the dump as-is (silent wrong answers on a malformed dump), or REFUSE a dump with a gap (a new error on `loadState` and on persistence auto-load, which would make a page fail to start; judged worse than serving less history). `historyFloor` becomes the block before the oldest record kept, so the existing refusal names it ("history starts at block X"). Site: `loadHistory`, documented on `SerializedState.history` in `src/types.ts`.
3. **A node WITH `stateHistory` always writes the field, possibly `[]`; a node without it writes no key at all.** So the "no history" dump of a node that never used the feature is byte-for-byte what it was (asserted: `'history' in dump === false`), and an empty array unambiguously means "a history node that holds no records yet". Site: `dumpState`.
4. **Only `stateHistory` reads the field.** A node with the INTERNAL `recordChangeSets` switch alone (tests, and later `computeStateRoot`) ignores it, like a node without the option: the field is the undo log, and only the option retains one. Site: the end of `loadState`.
5. **Format and names.** `SerializedHistoryBlock` (exported type, like `SerializedBlock`), one per retained block, oldest first: `number`, `accounts` (RLP or `null`), `code` (hex or `null`), `storage` (address -> slot -> hex or `null`), `storageCleared` (address list). `null` means ABSENT, kept distinct from an empty value (`0x`) because an absent account reads differently from an existing empty one. Keys are `0x` lowercase hex, the dump's existing convention (never the internal packed keys); the loader lowercases addresses. `version` stays 1 (documented on `SerializedState`).
6. **No changeset in this task**, following `state-history-point-reads` decision 1 and `historical-eth-call` decision 10: `state-history-docs-and-worker` owns the feature's one `minor` changeset, and its forward-pointer already lists persistence through `dumpState` / `loadState`.
7. **The bundle-size pin is re-pinned** to 441.4 KB raw / 133.0 KB gzip (from 439.9 / 132.5), measured after `pnpm build`, with a history entry in `DEFAULT_ENTRY_BASELINE`'s comment in `packages/benchmarks/test/evm.spec.ts`.
8. **Test changes outside the new battery:** the shared IndexedDB reload flow (`test/helpers/persistence-reload.ts`) now creates BOTH phases with `stateHistory: {blocks: 16}` and compares historical point reads and a pinned `readContract` across the real reload (both engines, via the two reload specs, which now pass the pinned block numbers to the read phase); `readAll` in `test/helpers/state-history.ts` and `executeAll` / `READER` in `test/helpers/historical-call.ts` are exported for the new battery (`test/helpers/state-history-persistence.ts`).
