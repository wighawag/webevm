# CONTEXT — webevm domain language

The domain glossary for `webevm`. Agents and skills use THIS vocabulary when naming modules, tests, and discussing the system. Architectural rationale lives in `docs/adr/` (decisions); product framing lives in `work/specs/`.

**RENAMED 2026-08-16.** This package was called `embedded-eth-node` through 0.4.0 and is `webevm` from 0.5.0 on (`docs/adr/0011-the-package-is-named-webevm.md`). Live surfaces (source, tests, package metadata, this file, the root README, CI) say `webevm`. DATED RECORDS DELIBERATELY DO NOT: `work/tasks/done/`, `work/tasks/cancelled/`, `work/notes/`, `work/specs/dropped/`, `docs/spikes/` and `packages/webevm/CHANGELOG.md` still say `embedded-eth-node`, because they were true when written and rewriting them would make past records claim a name that did not exist yet. What separates the two is whether a document will be ACTED ON again, not where it lives: `work/tasks/backlog/` and `work/questions/` were renamed in full, since a backlog item is executed later and its acceptance checks have to name paths that exist. Read the old name as this package, and translate any path you find there: `packages/embedded-eth-node/…` is `packages/webevm/…`, and the subpath `embedded-eth-node/revm` (or `/worker-entry`, `/worker-host`, `/worker-client`) is `webevm/…`. ADRs 0001-0010 sit between the two and were split down that line: they are consulted as current guidance, so their import paths and repo paths were corrected in place, while their prose about what was true at the time was left saying `embedded-eth-node`.

## What webevm is

A slim, execution-only in-browser EIP-1193 Ethereum node built on `@ethereumjs/vm`: a transport-agnostic core with optional Web-Worker hosting and IndexedDB persistence, which implements only the read + signed-raw-tx methods a viem/wagmi client actually uses and fails loudly at its intentional edges instead of faking success.

## Core domain terms

- **slim node** — the object `createNode()` returns: `{request, mine, dumpState, loadState, onNewHead, getStateRoot, dispose}`. `request()` is an async EIP-1193 method, which is what lets the SAME object work unchanged on the main thread or across a Worker boundary.
- **execution-only** — the node executes signed transactions and reads; it holds no keys and implements no account or signing methods. `eth_sendTransaction`, `eth_accounts`, `eth_sign`, `personal_*` and `wallet_*` throw a real `-32601` rather than faking success.
- **honest edge** — the convention that an unimplemented or deliberately-absent method fails LOUDLY with a real JSON-RPC error, never a plausible-looking fake result. The node's `-32601` surface is a feature, not a gap.
- **state mode** — `stateMode: 'none' | 'trie'`. `'none'` (default) is `OverlayStorageStateManager`, our `SimpleStateManager` subclass: plain Maps, no trie, no state root. `'trie'` is `MerkleStateManager`: a real Merkle-Patricia root, which is what makes the node conformance-testable against `ethereum/tests` GeneralStateTests. See `docs/adr/`.
- **storage overlay** — ONE CHECKPOINT'S WORTH OF STORAGE CHANGE, and the unit `stateMode:'none'` storage is built from: the slots written since that checkpoint (`Map<address, Map<slot, value>>`) plus a tombstone set of the accounts CLEARED in it. Storage is a STACK of overlays: a checkpoint pushes an empty one (copying nothing, at any state size), a commit merges the top one down, a revert drops it, and a read walks down until it finds the slot or an overlay that cleared the account. It replaced `SimpleStateManager`'s flat `${address}_${slot}` map, which every checkpoint copied WHOLE — once per EVM message frame. Say *overlay*, never "diff frame" or "journal frame": *frame* already means an EVM message frame (and the frame budget below), and *journal* already means the one `@ethereumjs/evm` keeps ABOVE the state manager. `docs/adr/0009-none-mode-storage-is-per-account-with-per-checkpoint-overlays.md`.
- **packed storage key** — the string a storage slot is keyed by inside `stateMode:'none'` storage: TWO BYTES PER UTF-16 CODE UNIT (10 code units for an account, 16 for a slot), built by `src/storage-keys.ts` and by nothing else. It replaced the `0x`-hex key in 2026-08 and is worth 70-73% of a cold revm storage access, which is only claimable because the node owns the representation (ADR 0009's amendment; `docs/spikes/revm-state-store-packed-storage-keys/`). Say *packed* for this and reserve *hex key* for the two places that still are one and must stay one: ACCOUNTS and CODE (`address.toString()`, `SimpleStateManager`'s own keys, ADR 0005) and the SERIALISED `dumpState` / `loadState` format (`liveStorage()` converts on the way out). The reason it is one module rather than one helper per side is the failure it prevents: the async `putStorage` and the synchronous `storageAt` are two routes into the same slot, and two key formats that each work make every cross-route read a MISS — which reads as ZERO at identical gas, so no gas gate, receipt diff or dump comparison can see it.
- **sender mode** — `senderMode: 'recover' | 'trusted'`. `'recover'` (default) derives the sender with ecrecover, as a real node does — on the installed engine's secp256k1 when it offers one, otherwise `@ethereumjs/tx`'s, the two being held to authenticating identically, refusals included. `'trusted'` takes a caller-supplied sender and skips ecrecover entirely, via the `evm_sendRawTransaction*As` cheats. Either way the answer is ONE value the node decides at parse time and then CARRIES (to the engine as `TransactionRequest.sender`, to the receipt's `from`) — say *the claimed sender* for what `'trusted'` was handed and *the recovered sender* for what a signature yields, and note that the two may DIFFER, which is the whole point of the mode and the case a re-recovering engine gets silently wrong. The word *pin* is retired here: the node used to pin the sender by SHADOWING `getSenderAddress()` on the transaction instance, and that mechanism is gone. See `docs/adr/`.
- **cheat method** — an `evm_*`-namespaced method that does something a real node would not (mutate state with no transaction, or trust a claimed sender). Deliberately namespaced so it can never be mistaken for standard behaviour.
- **the gate** — the cross-backend assertions in `packages/benchmarks`: every EVM backend must charge the same EXECUTION gas and produce the same keccak-chain result for the same call. Gas equality (not result equality) is what makes an interpreter swap safe, because engines that disagree on gas disagree on where execution runs OUT of gas, and a client replaying the chain would fork.
- **conformance differential** — the library's own test that runs the same signed transactions through the node AND a trie-backed `@ethereumjs/vm` `runTx` reference, diffing receipts field by field plus post-state. The strongest correctness bar in the repo. That reference is the oracle for the receipt and post-state steps, NOT for all of them: the block-environment step diffs what a contract read (`BASEFEE` / `PREVRANDAO` / `COINBASE` / `NUMBER` / `TIMESTAMP` / `GASLIMIT`) against the node's own block PLUS the `blockEnv` it was configured with (`COINBASE` and `PREVRANDAO` against the configuration specifically — which the RPC block did not report until 2026-08-11 and now does, so that half of the split is retainable rather than forced, and unwinding it is its own change), and the value-bearing-read step pins an absolute succeed/fail statement per sender AND per value, to the wei, because the reference is a separate hand-built chain with its own timestamps and a zero coinbase and a refused read produces no receipt at all, so those two classes of bug are structurally invisible to it. Each of the two says so at its own `THE ORACLE IS ...` comment in `packages/webevm/test/helpers/conformance.ts`; putting them back on the reference destroys the property they exist to have.
- **engine** — THE EVM BEHIND THE NODE: an object implementing `Engine`, passed as `createNode({engine})` and reported back as `node.engine`. ONE interface, TWO operations: `call` executes a read-only call (return data + EXECUTION gas + whether it failed) for `eth_call` / `eth_estimateGas` / `eth_fillTransaction`'s estimation, and `transact` executes a signed transaction AND COMMITS it, reporting the neutral `TransactionResult` a receipt is built from (status, gas used net of refunds, effective gas price, logs in emission order, the bloom, any created address). What differs between them is a transaction's VALIDITY rules — a read relaxes them (base fee, block gas limit, EIP-3607) and cannot commit, a transaction relaxes nothing — not their engine-ness, which is why it is one interface and not two. Default `@ethereumjs/evm`, on both; the shipped alternative is `createRevmEngine()` from the optional `webevm/revm` subpath (revm-wasm, `stateMode:'none'` only — it refuses `'trie'` at construction). BOTH operations are REQUIRED: an engine that brings only one is refused at `createNode()`, so a node runs exactly ONE EVM and `node.engine` names the one that answered its reads AND executed its transactions. It is never a name the core resolves — always an injected object, so the core imports no engine a consumer did not (`docs/adr/0006-the-engine-is-an-injected-object-not-a-named-string.md`, whose first amendment records the widening and whose second records the contraction). What is NOT the engine's, on any engine: block construction, `cumulativeGasUsed`, receipt assembly, the RPC layer, transaction parsing and sender derivation — and, since `replayed-and-invalid-transactions-are-rejected-as-the-nodes-own-errors`, the REFUSAL of a transaction the node will not admit into a block (the block gas limit, the intrinsic-gas floor, the nonce, and whether the sender can cover `value + gasLimit * maxFeePerGas`). Every engine enforces those four itself and none can say them in a way a client can use (`Transaction(NonceTooLow { tx: 0, state: 1 })` on one, `the tx doesn't have the correct nonce…` plus a block dump on the other), so the node answers them ABOVE the seam, in geth's vocabulary at `-32000`, and the engines' own checks stay as the backstop underneath — the refusal is then identical on every engine rather than merely present on all of them — those are the node's, and the SENDER in particular crosses as a required value on the request (`TransactionRequest.sender`) rather than as something an engine reads off the transaction, because `senderMode:'trusted'` admits a claimed sender the signature disagrees with (amendment 3 of `docs/adr/0006-...`). *Sender derivation* stays the node's in the sense that matters — which message is signed, EIP-2's low-`s` rule, what the wire's `v` means, and therefore whether the transaction is admitted at all — but an engine MAY lend the node the CURVE STEP behind it, through the seam's one optional operation `ecrecover(hash, recoveryId, r, s)`, which `webevm/revm` implements from the secp256k1 its `0x01` precompile already carries (amendment 4 of `docs/adr/0006-...`). Say *the ecrecover primitive* for that lending and keep saying *sender derivation* for the decision: an engine is asked a question about a SIGNATURE and never one about a TRANSACTION, so it can neither admit a transaction the node would refuse nor refuse one it would admit. State is not the engine's either: on both engines it stays the node's, read and written through host callbacks with nothing copied across (`docs/adr/0010-revm-reads-and-writes-through-host-callbacks-the-node-keeps-owning-state.md`). **RE-WIDENED 2026-08-10** by `re-widen-the-engine-seam-to-cover-transactions`: this entry used to mean the read path and ONLY the read path, and set the condition "do not re-widen *engine* to mean the EVM behind the node until a spec actually moves transactions onto it". `work/specs/tasked/revm-engine-behind-runtx.md` is that spec, so the condition was MET and the term is widened rather than quietly rewritten. *read engine* is retired as a term: there is no `ReadEngine` type, no `node.readEngine`, and — since `revm-executes-the-first-transaction-with-commit` made `transact` required — no such thing as **"an engine that implements only the read half"** either. That phrase was this entry's sanctioned way to describe the transitional revm engine; it named a state the seam no longer admits, so do not reach for it.
- **worker host**: the WORKER-thread half of the optional comlink pair, published as `webevm/worker-host`, and the ONE place the `SlimNode` proxy that crosses a thread boundary exists. `exposeNode({createEngine})` is the whole of a consumer's own worker module: the main thread's options still travel through `createWorkerNode()` untouched and only the ENGINE is the worker thread's business, built there because an engine cannot be cloned across the boundary and the core must never name one (ADR 0006). Say *worker host* for that thread-side api and keep saying *worker entry* for `webevm/worker-entry`, which is the same api plus an import-time `expose()`, the side effect that makes `new Worker(new URL('webevm/worker-entry', ...))` a one-liner and that makes it unusable as a library, which is why the two are separate modules. The proxy being SINGULAR is a correctness property, not tidiness: it is a literal typed `Required<SlimNode>`, so a field added to that interface is a BUILD error at the proxy rather than an `undefined` read on a consumer's main thread (which is what happened to `senderMode`, hidden by an `as any` in `worker-client` that is now gone); `Required<>` rather than a bare `SlimNode` so that an OPTIONAL member added later is covered too, which the runtime parity check in `test/helpers/worker-roundtrip.ts` structurally cannot be (it enumerates the keys of a reference node INSTANCE). The option is `createEngine` (a factory called once per node), never `engine`, because *engine* means the injected OBJECT everywhere else in this vocabulary. A `createEngine` that is not a factory is REFUSED, and the refusal is a VALUE rather than a throw: `exposeNode()` still calls comlink's `expose()` (a module that throws before reaching it registers no message listener, so the main thread's `createWorkerNode()` never settles and the reason reaches only the worker's console), the worker console gets the message immediately, and `createNode()` rejects with the same text so the caller gets it too. Say *both signals* for that pairing: a hang is the least legible failure available and the honest-edge convention forbids trading one signal for the other.
- **serialisation point** — THE SINGLE PROMISE CHAIN EVERY PUBLIC ENTRY POINT ON A NODE QUEUES ONTO, so one node runs exactly ONE piece of work at a time: `request`, `mine`, `dumpState`, `loadState` and `getStateRoot`, wrapped where the node object is built and NOWHERE else. Say *serialisation point* for the mechanism and *one request at a time* for the property a consumer gets. *lock* is fine as informal shorthand for it and the code uses the word, but keep the distinction it hides in view: there is ONE thread, so what this prevents is not two executions running at once, it is one execution INTERLEAVING with another at the other's await points. Interleaving is the defect: reads and transactions open checkpoint levels on the ONE state manager a node owns, `commit()` merges the top level down and `revert()` discards it, and neither knows who opened it, so an `eth_call` arriving mid-transaction reverted the level the transaction had just committed into — a lost nonce, state TORN at a message-frame boundary, an `eth_call`'s own `SSTORE` committed, two transactions handed the same block number, every one of them with a success receipt. It is per NODE, which is per STATE MANAGER by construction (a node builds its own and an engine binds to one node), it covers EVERY request rather than only the executing ones (a non-executing read walks UNCOMMITTED levels and reports state no block contains — measured, not assumed), and it lives in `createNode` rather than in an engine or a transport, because write-versus-write interleaves too and `worker-host` forwards straight to `node.request`. The ONE rule it imposes on a consumer: a `persistence.save()` hook may not await a call back into the node, because that hook is awaited while the chain is held (an `onNewHead` subscriber MAY, since the emit does not await, so its request queues behind the block it was told about). That rule is DOCUMENTED AND NOT ENFORCED, deliberately, and the failed attempt is worth knowing about before anyone repeats it: a flag raised around the awaited hook cannot distinguish the hook's own re-entrant call from any other caller's request arriving during its I/O (there is no `AsyncLocalStorage` in a browser), so it refused an innocent poller four times off a 20 ms save and told it each time that it had caused a deadlock. A false refusal carrying a confident wrong diagnosis is worse than the hang it replaces. `docs/adr/0012-one-request-at-a-time-the-node-serialises-its-whole-public-surface.md`, `packages/webevm/test/concurrency.spec.ts`.
- **tick-offset scan** — the harness the concurrency battery is built from, and the reason it is a test rather than a flake: the second request is issued after an EXACT number of microtask ticks, a fresh node per offset, and the whole range is swept, so an overlap is DETERMINISTIC instead of hoped for. Ticks, not timers — `setTimeout` lands between macrotasks, i.e. after an execution that never yields to the task queue has finished, while `@ethereumjs/evm` yields to the MICROTASK queue as it interprets. Every scan also reports `issuedWhilePending` (how many offsets really did overlap), because a scan whose window has moved passes every assertion while testing nothing — the same vacuous pass `transactionsByEngine` exists to prevent in the conformance battery.
- **frame budget** — 16.6 ms, the 60fps target. The benchmark's `frame` row (N small view reads back to back) is measured against it, because the consuming use case is an in-browser on-chain game.
- **promptGuidance** — the per-repo NUDGE namespace in `dorfl.json` whose members (currently just `testFirst`) strengthen the wording in the worker's in-band prompt. NOT a gate: the `verify` step is still the only acceptance bar.
- **work/ contract** — the on-disk system this repo uses, defined by the reference docs in **`work/protocol/`** (copied here by `setup`): `WORK-CONTRACT.md` (the contract), `CLAIM-PROTOCOL.md`, `REVIEW-PROTOCOL.md`, `task-template.md`, `spec-template.md`, `ADR-FORMAT.md`. Three REGIME umbrellas — `notes/` (capture buckets), `tasks/` (the build board), `specs/` (the spec lifecycle) — plus top-level `questions/` and `protocol/`. One markdown file per item, status = the folder it lives in (never a field). Capture buckets: `notes/ideas/` (proposed), `notes/observations/` (spotted, unverified, append-only), `notes/findings/` (verified EXTERNAL ground truth, each with a `source:`). Our own architecture belongs in this file and `docs/`, never in `findings/`. ADRs (`docs/adr/`, format in `work/protocol/ADR-FORMAT.md`) record what WE decided and why.

## Conventions

Standing per-change rules agents must follow in this repo.

- **Every user-facing change needs a changeset.** Run `pnpm changeset` (or hand-write a file in `.changeset/`) describing the change and its semver bump. This repo publishes `webevm` to npm via changesets; a release without one silently ships unversioned. Not currently enforced by the `verify` gate — to enforce it, add your own check (e.g. `changeset status --since=main`) to `verify` in `dorfl.json`.
- **The pnpm version is PINNED** by `packageManager` in the ROOT `package.json` (an exact version plus its integrity hash), and that is the ONLY place it is written. pnpm self-forwards to it, so a bare `pnpm` runs the pinned version whatever the machine has installed — the same mechanism as `dorflCmd` below, and for the same reason. To bump: edit the field (`corepack use pnpm@<version>` writes the version AND the hash for you), run `pnpm install`, and check the lockfile diff. The CI and release workflows pass NO `version` input to `pnpm/action-setup`, deliberately: they read this field, so CI cannot drift from a developer's machine. The drift this closed was real and silent — the workflows pinned a floating `version: 10` while a system pnpm 11 ran locally, and pnpm 11 rewrote `pnpm-workspace.yaml` on every install and failed `pnpm build` with `ERR_PNPM_IGNORED_BUILDS`. Which dependency build scripts run is a recorded decision too, in `ignoredBuiltDependencies` in `pnpm-workspace.yaml`, with the reason each one is safe to skip written beside it: pnpm asks once per new one, and from pnpm 11 an unanswered question is a hard install failure rather than a warning.
- **The dorfl version is PINNED** via `dorflCmd` in `dorfl.json`, pointing at the project-local `node_modules/.bin/dorfl`, so bare `dorfl` self-forwards to the version in this repo's `devDependencies` rather than floating with whatever is globally installed. To bump: change the `dorfl` devDependency, `pnpm install`, then `dorfl sync` to re-sync `work/protocol/`.
- **Never commit a wasm artifact.** The revm module is consumed as the `revm-wasm` npm package (prebuilt `.wasm` in the tarball, zero runtime dependencies), so `packages/benchmarks` needs no build step and no vendored blob; the benchmark spec copies the package's `.wasm` into the served directory at test time. If another wasm engine is ever added, add it the same way rather than checking bytes in.
