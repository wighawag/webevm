# A fork's gas RULES on the read path are the node's admission, and intrinsic gas stays OFF the seam

Prague and Osaka bring three gas rules the node did not implement: EIP-7623's calldata floor (a transaction pays at least `21000 + 10` gas per calldata token), EIP-7825's per-transaction gas cap (16,777,216) and EIP-7702's per-authorization charge (25,000 per entry). ADR 0008 refused both forks until the node could cost them, and its backlog task set a tripwire: before adding the floor, evaluate moving intrinsic gas onto the engine seam's read request (`ReadCallRequest`), so that the node computes it once and the engine merely reads it, because the floor was expected to be the "second fork-dependent term" that decision had been deferred until. **We evaluated it and do not move it.** None of the three rules is something an engine has to subtract. Each is a rule about which reads and transactions the node admits and which gas limits it recommends, so the node enforces all three ABOVE the seam, identically on every engine, and the one number that does cross the seam is unchanged.

## What the engine actually needs, and why the floor is not part of it

The seam's read request states one gas figure: `ReadCallRequest.gasLimit`, the gas available to EXECUTION. The default engine hands it to `runCall` as it is. `webevm/revm` converts it into a transaction gas limit by adding the shared `intrinsicGas()` back, because revm charges intrinsic gas out of the transaction limit, and subtracts the same number from what revm spent. That conversion is the only place an engine needs intrinsic gas, and it is already drift-proof: both callers use the one function in `src/intrinsic-gas.ts`, asked of the one `Common` instance the node hands the engine at `connect` (ADR 0008, second amendment).

The floor is not a term of that conversion. It is a lower bound on the transaction's TOTAL, and revm enforces it by refusing a limit below it (`GasFloorMoreThanGasLimit`), not by charging it out of the limit. Nothing an engine could do with a floor on the request would be faithful: running the read at `max(budget + intrinsic, floor)` hands execution more gas than the node asked for, so the two engines would disagree about where a call runs out of gas, which is the one disagreement the benchmark gate exists to catch. So the node never asks for such a read in the first place. The authorization charge needs nothing from an engine either, which a read request carries no authorization list to be charged for, exactly as it carries no access list (`accessListGas` in `src/intrinsic-gas.ts`).

## The decision

`src/intrinsic-gas.ts` gains the floor as a SECOND function beside `intrinsicGas()` and `accessListGas()`, fork-gated on the node's `Common` (`isActivatedEIP(7623)`, the table `runTx` consults), plus the authorization charge and the cap, both gated the same way. The node, and only the node, applies them:

- **Every read it hands an engine reaches the floor.** Its total (execution budget plus intrinsic gas) is at least the floor, or the read is refused in geth's words before an engine sees it, so the answer is the same on both engines. revm's own refusal stays as the backstop underneath, as it already is for the transaction path.
- **The cap is a rule about TRANSACTIONS, and a read is not one.** geth skips it for `eth_call` and keeps it for `eth_estimateGas`, and `@ethereumjs/evm`'s `runCall` never enforced it. So the node does not hold a read to it, and the revm engine lifts it on its reads with `revm-wasm`'s `disableTxGasLimitCap` (0.5.0), the same kind of simulation switch as `disableBlockGasLimit`: engine vocabulary, kept inside the engine's `call` rather than placed on the seam's request, and refused by the binding on a committing execution. The default read budget stays 30,000,000 on every fork.
- **`eth_estimateGas` searches only valid gas limits**: its lower bound is the larger of the intrinsic charges and the floor plus the request's list charges (see Consequences for why the lists are added to the floor), and its upper bound is the block gas limit capped by EIP-7825 (which is what geth's estimator does from Osaka on).
- **A transaction below the floor, or above the cap, is refused at submit**, beside the existing below-intrinsic and over-block-gas-limit refusals, in geth's vocabulary.
- **A read carrying an EIP-7702 authorization list is charged for it and executes with its delegations applied**, written into a checkpoint the read runs in and reverts (as state overrides are), so neither engine sees the list.

## Considered options

- **Move intrinsic gas onto `ReadCallRequest` (the deferred option).** Additive for an engine that receives the request, and it would let an engine outside this repo convert the budget without re-implementing the formula. Rejected for now because it removes no drift that exists (the two callers already share one function and one `Common`), because it would not carry the floor anyway, and because it changes a public type third-party engines implement for a benefit no current engine needs. Revisit when an engine outside this repo needs the number and cannot import it; that is a different trigger from a fork rule arriving.
- **Put the floor (or a minimum gas limit) on the read request** so revm can raise the limit itself. Rejected: see above, execution would get more gas than the node asked for, on one engine only.
- **Carry the request's access list and authorization list on the read request**, which would make an estimate with a list exact where the floor binds. Rejected for the reason `accessListGas` records: it is a seam widening that needs the list pre-warmed identically on both engines, which is a change to the seam, not to an estimate.

## Consequences

- **One estimate edge over-estimates, identically on both engines.** Because the node's read carries no access or authorization list, the lowest gas limit it can probe without revm refusing the read is the floor PLUS those lists' charges, where the protocol's is the larger of the floor and the intrinsic total. For a calldata-heavy request with a list, whose answer is decided by the floor, the estimate is therefore high by at most the list charges. That is the safe direction (a client uses the estimate as a gas limit, and unused gas is not charged).
- **Lifting the cap on reads needed the engine's binding to offer it.** Until `revm-wasm@0.5.0` revm applied EIP-7825 to every execution with no way out, so the node first held reads to the cap on both engines (stricter than geth) rather than let one engine serve a read the other refused. The switch removed that deviation. A third-party engine that enforces the cap on its reads would refuse what the default engine runs, which is the same obligation every simulation switch already places on an engine's `call`.
- **The seam types are unchanged**: no field is added to `ReadCallRequest`, `TransactionRequest` or `EngineContext`, so a third-party engine needs no change to serve Prague or Osaka beyond executing the fork's rules itself.
