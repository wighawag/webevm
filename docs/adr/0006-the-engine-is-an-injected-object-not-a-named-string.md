# The engine is an INJECTED OBJECT, not a named string

> **Amended 2026-09-28** (`rename-statemode-to-computestateroot`): the `connect(context)` context no longer carries `stateMode`; it is `{stateManager, common, getBlockHash}`. No engine needs to know whether the node computes a state root now that every node runs on the same flat state (ADR 0014), and the option itself is now `computeStateRoot: boolean`. An engine still refuses a configuration it cannot serve by throwing from `connect` (the revm engine refuses a hardfork it cannot cost, ADR 0008).

> **Amended three times, all 2026-08-10.** The decision below is UNCHANGED — an engine is still an injected object and never a name — but the seam's SCOPE widened from reads to reads AND transactions (`re-widen-the-engine-seam-to-cover-transactions`), so `ReadEngine` is now `Engine`, `node.readEngine` is now `node.engine`, and the second and fourth consequences below are superseded: see [amendment 1](#amendment-1-the-seam-covers-transactions-too-so-the-type-is-engine-and-the-property-is-nodeengine). Then `transact` stopped being optional (`revm-executes-the-first-transaction-with-commit`): see [amendment 2](#amendment-2-transact-is-required-and-the-fallback-is-gone). Then the SENDER became a required value on the transaction request rather than something an engine reads off the transaction (`trusted-sender-transactions-run-on-the-write-engine-as-the-claimed-sender`): see [amendment 3](#amendment-3-the-sender-crosses-the-seam-as-a-value-not-as-a-method-an-engine-calls).

`createNode()` takes an EVM engine as an OBJECT implementing the `ReadEngine` type (`createNode({engine: await createRevmEngine({wasm})})`), never as a name the core resolves (`createNode({engine: 'revm'})`). The string form is the more obvious API and it is the one we rejected: a name only means something if the core can turn it into code, so the core would have to `import` every engine it can name. That import is unconditional in the module graph, so a bundler cannot tree-shake it away, and a JS-only consumer — the DEFAULT consumer, who never asks for revm — would ship a wasm engine they never call. Story 3 of `work/specs/tasked/revm-engine-behind-eth-call.md` is precisely "I pay nothing for a feature I do not use", so a string option would defeat the feature's own premise. An injected object inverts that: the core references only the interface, the consumer's own import decides what is in their bundle, and an engine the core has never heard of works exactly as well as one we shipped.

This is recorded because it is public API shape (hard to reverse once consumers pass `engine:`), and because the alternative is what a reader would expect to find.

## Consequences

- **The engine is CONSTRUCTED by the consumer, and its context comes from the node.** An injected object exists before the node does, so it cannot capture the node's state manager at construction. The seam therefore has exactly one lifecycle hook, `connect(context)`, called once during `createNode()` with `{stateManager, common, stateMode}`. It is also the honest place for an engine to REFUSE a configuration it cannot serve (ADR 0005: the revm read path has no synchronous view of `MerkleStateManager`, so `stateMode:'trie'` must throw), because a throw there fails node construction rather than the first opcode.
- **`node.readEngine`, not `node.engine`.** Only the READ path (`eth_call`, `eth_estimateGas`, `eth_fillTransaction`'s estimation) is routed through the engine; transactions run on `@ethereumjs/vm` regardless. A node with an injected engine therefore runs TWO EVMs, and an unqualified `node.engine` would let a bug report attribute a receipt to an engine that never touched it. The property carries its scope in its name and reports identity only (`{id}`), so it survives the comlink Worker boundary as a plain value. *(Superseded by the amendment: the property is `node.engine`, and the identity-only `{id}` half stands.)*
- **Purity is the ENGINE's business, not the node's.** The node's pure-read helper no longer checkpoints or resets EIP-2929 warmth; the default `@ethereumjs/evm` engine does both, because both are requirements of THAT EVM. Per ADR 0005, `SimpleStateManager.checkpointSync()` copies all three state maps and clones every account (0.384 ms per call at 2002 accounts, larger than the entire revm read it would wrap), so an engine that structurally cannot commit must not pay for it.
- **The interface stays the smallest thing that serves a read**: return data, execution gas, and whether it failed. Transactions are deliberately NOT designed for here — `work/specs/ready/revm-engine-behind-runtx.md` owns that shape, and guessing it now would get it wrong. Anything a future engine needs and this context lacks (block hashes, for instance) is an additive field on `ReadEngineContext`. *(Discharged by the amendment: that spec came, and the transaction shape was designed then rather than guessed here. The additive-widening rule stands, on `EngineContext`.)*

## Amendment 1: the seam covers TRANSACTIONS too, so the type is `Engine` and the property is `node.engine`

2026-08-10. `work/specs/tasked/revm-engine-behind-runtx.md` moved transaction execution onto the seam, which is the condition the original text (and `CONTEXT.md`'s glossary) named for widening the word *engine*. The seam is now ONE interface with TWO operations — `call` (read-only) and `transact` (executes and commits) — the default `@ethereumjs/evm` engine implements both, and the node's mining path executes through it rather than calling `runTx` itself. **Nothing about the injected-object decision changed**; what changed is what an engine is asked to do.

**Why one interface rather than a second one.** The read and write paths differ in a transaction's VALIDITY rules, not in their engine-ness: a read relaxes them (base fee, block gas limit, EIP-3607) and cannot commit, a transaction relaxes nothing. That asymmetry belongs to the two OPERATIONS, and stating it in one place where both are visible beats splitting it across two interfaces that could then be pointed at two different EVMs — two identifiers that can disagree, for no gain. There were no third-party engines to break.

**The name broke rather than being aliased.** `ReadEngine` → `Engine`, `ReadEngineContext` → `EngineContext`, `ReadEngineInfo` → `EngineInfo`, `node.readEngine` → `node.engine`, with no deprecation alias, across roughly 150 occurrences in about thirty files inside this repo. A shim would have left two words for one concept from the day it landed, and there is nothing outside this repo depending on the old one. `CHANGELOG.md` is NOT rewritten: it records what shipped under the name that shipped.

**What the seam gained, and it is the point of the change: a neutral transaction result.** `TransactionResult` carries what a RECEIPT needs from an EVM and nothing else — status, gas used (net of refunds), effective gas price, logs in emission order, the logs bloom, any created address — in raw bytes and bigints rather than `@ethereumjs/*` classes. `runTx`'s `amountSpent`, `gasRefund`, `minerValue`, `accessList` and `execResult` are deliberately absent: no receipt reads them, and a field that exists because one engine returns it is what makes two engines incomparable. The effective gas price is now the ENGINE's answer (the node's legacy-safe computation moved behind the default engine) because the engine that executed the transaction is the engine that charged it.

**What did NOT move, on any engine**: block construction, `cumulativeGasUsed`, receipt assembly, the RPC layer, transaction parsing and sender recovery. And `@ethereumjs/vm`'s two `skip*Validation` flags stayed INSIDE the default engine rather than becoming neutral request fields — they are one EVM's vocabulary, and worse, `revm-wasm` REFUSES to combine its equivalent relaxation with committing, so a neutral field would have been a promise the next engine could only throw at. The reasoning is recorded at that code site (`src/engine.ts`).

**`transact` is OPTIONAL, and that is transitional rather than a design.** An engine that omits it leaves the node's transactions on the node's own `@ethereumjs/vm`, which is exactly what every non-default engine did before this change — which is why it is what preserves behaviour. The shipped `webevm/revm` engine is in that state until its write half lands, so requiring the method would have meant refusing every transaction on a revm-backed node. A `transact` that is PRESENT but not a function is refused at construction, alongside the existing refusals, because a half-built engine silently mining on `@ethereumjs/vm` is the same class of lie as the fallback this ADR's other consequence exists to prevent. *(Superseded by amendment 2: the method is required and the fallback is deleted.)*

**`node.engine` reports the engine that was INSTALLED**, still identity-only (`{id}`), still a plain value across the comlink boundary. On a node whose engine implements only the read half, a receipt therefore cannot be attributed to that id — the pre-existing two-EVM shape, now stated in `CONTEXT.md` and the README rather than encoded in a property name. *(The two-EVM half is discharged by amendment 2; the identity-only half stands.)*

## Amendment 2: `transact` is REQUIRED, and the fallback is gone

2026-08-10, by `revm-executes-the-first-transaction-with-commit`. The optional marker had exactly one reason: the shipped `webevm/revm` engine had no write half, so requiring the method would have meant either refusing every transaction on a revm-backed node or changing what one does, and amendment 1's bar was that nothing changes. **That task removed the reason** — revm now executes and commits transactions against the node's own state — so the transitional shape is gone with it rather than left as a vestigial capability check in a published package:

- `Engine.transact` loses its `?`, and `connectEngine` refuses an engine whose `transact` is MISSING or is not callable, in one guard and one message. The two were separate cases only while absence was legal.
- `src/node.ts` loses `transacts(engine) ? engine : defaultEngine` and the second, internally-built engine it selected; `src/engine.ts` loses `transacts()` and the `TransactingEngine` type. The node builds the default engine only when the consumer passed none.
- **The misattribution amendment 1's second consequence warned about is therefore GONE rather than documented.** A node runs exactly one EVM, so `node.engine` names the engine that answered its reads and executed its transactions, and a receipt can be attributed to it. The phrase *an engine that implements only the read half* named a state the seam no longer admits; it is retired from `CONTEXT.md` with the rest of the transitional wording.

**What this costs a third-party engine**, stated plainly: an engine can no longer ship reads first and grow writes later. That was the whole convenience of the optional marker, and it is the right thing to lose — the alternative is a node that silently runs two EVMs, which is what this ADR's central decision (no silent substitution, ever) exists to prevent one layer up. There were no third-party engines to break, and an engine that genuinely cannot commit can implement `transact` as a throw, which surfaces at the transaction rather than at every transaction being quietly executed by something else.

## Amendment 3: the SENDER crosses the seam as a VALUE, not as a method an engine calls

2026-08-10, by `trusted-sender-transactions-run-on-the-write-engine-as-the-claimed-sender`. `TransactionRequest` gains a required `sender: Address`, and it is the node's authoritative answer to *who sent this transaction*: `msg.sender` of the top-level frame, the account charged, the nonce advanced, the `from` on the receipt. **An engine executes on behalf of it and derives nothing.** Amendment 1's "sender recovery did not move" still holds — recovery is the node's — but the RESULT of it now crosses the seam explicitly rather than being left on the transaction for an engine to fetch the same way `runTx` did.

**Why it could not stay implicit.** `senderMode:'trusted'` (ADR 0002) exists so a caller who already knows the sender can skip ecrecover, and it therefore admits a transaction whose CLAIMED sender differs from what its signature recovers to (a fabricated signature has no meaningful recoverable sender at all). The node used to express that by SHADOWING `getSenderAddress()` on the `@ethereumjs/tx` instance it was about to run — which worked only because `runTx` reads the sender through exactly that one call, and the node was the thing calling `runTx`. Once transactions cross the seam, the same trick becomes an undocumented convention holding ACROSS an engine boundary: an engine that recovers its own sender charges a different account, advances a different nonce, commits, and returns a receipt that looks entirely right. **The failure is silent**, and at the time this landed no test could see it (the trusted-sender suite never installed an engine).

- **The shadowing is GONE, not kept as a second mechanism.** `parseTx` decides the sender ONCE per transaction (recovered, or the claimed address) and hands it along with the transaction; transactions are parsed frozen again. One value reaches the engine, the receipt's `from` and the stored transaction, so "who the engine executed as" and "who the receipt names" cannot drift apart by engine.
- **The default engine PINS it for `runTx`, inside the engine.** `runTx` has no sender parameter, so `src/engine.ts` gives it a prototype VIEW of the transaction whose `getSenderAddress()` returns `request.sender`. That is this EVM's own vocabulary — exactly like the two `skip*Validation` flags — the node's transaction is never mutated, and the pin lives for one call. `webevm/revm` needs none of it: revm's execute takes `from` directly.
- **It is REQUIRED, and that is the structural half.** `{tx, block}` is no longer a transaction request, so an engine cannot be handed one without a stated sender. TypeScript cannot forbid an engine from ignoring the field and recovering anyway, so the other half is a test that CATCHES it: a transaction signed by one account and submitted claiming another, where both are equally valid senders (same nonce, both funded) so a re-recovering engine executes it happily and only the post-state disagrees. The trusted-sender suite is engine-parameterised for that reason and runs on both engines, asserting the same post-state literals.
- **What it costs a third-party engine**: nothing it should have been doing. An engine that recovers senders itself was already wrong on a `'trusted'` node; now it is wrong against a stated input.

## Amendment 4: an engine may lend the node `ecrecover` — the CURVE step, never the decision

2026-08-11, by `sender-recovery-uses-the-engines-ecrecover`. `Engine` gains an OPTIONAL `ecrecover(hash, recoveryId, r, s)` returning a 20-byte address or `undefined`. In `senderMode:'recover'` the node uses it when the installed engine has one and falls back to `tx.getSenderAddress()` when it does not. `webevm/revm` implements it at **zero additional bytes** — its `0x01` precompile is that same secp256k1 — which makes the recovery ~4.3x cheaper and a small transaction ~3x cheaper on that engine (`docs/spikes/sender-recovery-uses-the-engines-ecrecover/measurements.md`).

**This does NOT reverse amendment 3, and the distinction is the whole point.** Deciding *who sent this transaction* is still the node's, on every engine: the node computes the message hash, enforces EIP-2's low-`s` rule, converts the wire's `v` (27/28, `chainId * 2 + 35/36`, or a bare y-parity) into a 0/1 recovery id, and only then asks the curve. An engine is handed a question about a SIGNATURE and never one about a TRANSACTION, so it needs to know nothing about EIP-155, EIP-2718 or `senderMode`, and it can neither admit a transaction the node would refuse nor refuse one the node would admit. `TransactionRequest.sender` remains the authoritative answer and remains required.

- **EIP-2 in particular is not the engine's.** revm's implementation is the `0x01` precompile's, which NORMALISES a high-`s` signature and returns an address — correctly, because EIP-2 constrains transactions rather than the precompile. A node that simply forwarded `(hash, v, r, s)` would ADMIT, on the revm engine, a transaction the default engine REFUSES: silently, with a plausible receipt, attributed to the right signer. That is measured, not argued: removing the node-side check turns `test/revm-sender-recovery.spec.ts` red with the transaction mined and the balance moved.
- **It is the seam's ONLY optional operation, and that is a considered asymmetry.** `call` and `transact` are refused at construction when missing (amendment 2) because the node cannot supply them; this one it can, and always could. So the rule stated in amendment 2 — a capability the node cannot fill in is required — still holds, and this is on the other side of it.
- **What it costs a third-party engine**: nothing. Omitting `ecrecover` is the supported case and costs only the speed. An engine SHOULD implement it only when its module already carries secp256k1, and must implement it as the raw curve operation with no protocol opinions added.
