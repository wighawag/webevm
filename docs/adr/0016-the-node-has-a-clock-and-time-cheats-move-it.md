# The node has a clock, and time cheats move it, under the names the other dev nodes use

A mined block's timestamp comes from ONE function of the node, its CLOCK, which reads three settings in order: a NEXT TIMESTAMP (set by `evm_setNextBlockTimestamp` or `evm_mine`'s timestamp, used by one block, which must be later than the head's), else an INTERVAL (`anvil_setBlockTimestampInterval`: the parent's timestamp plus that many seconds, 0 repeating it), else the BASE (`blockEnv.timestamp` when pinned, the wall clock otherwise) plus an OFFSET (which `evm_increaseTime` and `anvil_mine`'s interval add to, and which a spent next timestamp moves so the clock carries on from it). With none of them set the clock is exactly what the node did before: `blockEnv.timestamp` or the wall clock, with no reference to the parent. `evm_mine` and `anvil_mine` (alias `hardhat_mine`) are `node.mine()` over RPC, inside the serialisation point. This answers the second half of the question left open by `work/notes/observations/2026-09-28-mined-block-timestamps-are-not-strictly-increasing.md` (whether the time cheats belong here: yes) and leaves the first half (whether the DEFAULT should be `max(wall clock, parent + 1)`) open.

Why they belong in an execution-only node: they are not account policy (ADR 0004) and they fabricate nothing a client could mistake for a real node's answer; they are cheats like the state cheats, and a consumer simulating a chain over months (interest accrual, vesting, TWAP oracles, any contract that reads `block.timestamp`) cannot exercise its contracts without them. The wall-clock default ties a chain's timestamps to how fast the host ran it, which an in-browser simulation cannot control.

Why these NAMES and wire shapes: they are the ones anvil, hardhat and ganache already answer, and the ones viem's test actions send (`increaseTime` and `setNextBlockTimestamp` as `evm_*` in every mode; `mine` as `anvil_mine` / `hardhat_mine [blocks, interval]`, or ganache's `evm_mine [{blocks}]`; the interval as `anvil_setBlockTimestampInterval`). A test written against anvil, or a `createTestClient({mode: 'anvil'})`, therefore runs against this node unchanged, which the battery checks with viem's own test client in all three modes. The results follow anvil: `evm_setNextBlockTimestamp`, `anvil_mine` and `anvil_setBlockTimestampInterval` return `null`, `evm_increaseTime` returns the TOTAL offset as a JSON number (ganache's contract too), `evm_mine` returns `"0x0"` (both), `anvil_removeBlockTimestampInterval` returns whether one was set. The `anvil_*` names break this repo's otherwise `evm_*` namespace for cheats, on purpose: no other dev node defines those methods, and a cheat's namespace exists to mark it non-standard, which `anvil_` does as well.

## Considered Options

- **This repo's own names (`evm_setBlockTimestampInterval`, an `evm_mine` with one timestamp only).** The first draft. Rejected: every caller already speaks anvil's dialect, and a second dialect would be a gap at exactly the place a caller expects none.
- **A wall-clock offset only (`evm_increaseTime` and `evm_setNextBlockTimestamp`, as hardhat).** Kept, but not sufficient alone: every block after a jump is still stamped from the wall clock, so two runs of the same chain differ by however long each took. The interval is what makes a simulated chain reproducible.
- **An equal next timestamp, as anvil admits.** Not taken: hardhat refuses it, post-Merge consensus forbids it, and the refusal reads in hardhat's words (`lower than or equal to previous block's timestamp`, at `-32000`). The one deliberate difference from anvil.
- **Make the default strictly increasing now.** Not taken here: it changes every existing node's timestamps (auto mining would run ahead of the wall clock in bursts) and is the observation's own question. An interval of one second gives a consumer that behaviour today, opt-in.
- **Put the clock in `dumpState`.** Rejected: it is a setting of the node running the chain, like the mining config, not a fact of the chain; a dump moved to another node should not carry a pending jump. `loadState` drops a pending next timestamp for the same reason (the loaded head may be past it).
- **`evm_setTime`, `evm_snapshot` / `evm_revert`, `evm_setAutomine`.** Out of scope: the first is ganache's millisecond clock reset (anvil accepts it with a heuristic), the others are not about time. Each would be its own change.

## Consequences

- A refused transaction spends nothing: the next timestamp is consumed only when its block is stored.
- With `blockEnv.timestamp` pinned (GeneralStateTest replay) every block still carries the pinned value until a cheat is issued; an interval counts from the pinned parent. A pinned clock is also what makes the battery's timestamps exact.
- The battery is `packages/webevm/test/helpers/block-clock.ts`, run on both engines; on revm it is the EXECUTED timestamp (a transaction stores `TIMESTAMP`) that is checked, not only the header.
