# Dev accounts, signing and impersonation live in `@webevm/devnode`, a `SlimNode` decorator funded at genesis

webevm's core holds no keys and implements no account or signing method (ADR 0004), and offers impersonation only as the trusted-sender primitive, leaving the account policy to "a higher layer" (ADR 0002). Dev tooling (rocketh's in-process chain first) needs that layer: dev accounts answering `eth_accounts` and signing, `hardhat_impersonateAccount`, and an export of the state for forge's `vm.loadAllocs`. We decided that this layer is a separate package in this monorepo, `@webevm/devnode` (`packages/devnode`), shaped as described below. Decided with the maintainer on 2026-11-20, from the spec `work/specs/tasked/dev-node-package.md`.

## The decisions

- **A separate package, never a subpath of `webevm`.** Its direct dependencies, approved by the maintainer: `@scure/bip39` and `@scure/bip32` (mnemonics), `@noble/curves` (message signing; `@ethereumjs/util` v10 exports no signing function), `@noble/hashes` (keccak), `@ethereumjs/tx`, `@ethereumjs/util` and `@eip-1193/over-port` (`serveOn`), with `comlink` as an optional peer for `/worker-host`; EIP-712 hashing is the package's own code. A subpath (`webevm/dev`) ships inside the core package, and ADR 0004 rules accounts out of that package "not even optionally". `webevm` is a PEER dependency of `@webevm/devnode`, with a minimum version that has the worker-host factory below, so a consumer never bundles two copies of the core.
- **Cheat ALIASES are the core's, account policy is the package's.** ADR 0016 put anvil's and Hardhat's names for mining and time into the core, on the principle that a cheat that is not account policy and fabricates nothing a client could mistake for a real node's answer belongs in the core, under the names the other dev nodes use. The same principle puts the `hardhat_` / `anvil_` names of the state cheats and the snapshots (`evm_snapshot` / `evm_revert`, `anvil_snapshot` / `anvil_revert`) in the core too. `@webevm/devnode` forwards them; it implements only what the core rules out: accounts, signing, impersonation, plus the alloc export.
- **The package is a `SlimNode` DECORATOR.** `wrapDevNode(node, options)` takes a `SlimNode` and returns a `Required<SlimNode>`: it overrides `request` (answering the account methods and forwarding everything else, errors included), `serveOn` (serving its own `request`, so a served port answers the account methods) and `dispose` (closing the ports it served, then delegating, since the inner node's `dispose` closes only its own); every other member delegates. Returning a node rather than a bare EIP-1193 provider is what lets the same object run on the main thread, over a `createWorkerNode()` proxy, and inside a worker, and lets it read `senderMode`.
- **Dev accounts are funded AT GENESIS, as anvil and Hardhat fund theirs.** anvil takes `--accounts` (default 10), `--balance` (default 10,000 ETH), `--mnemonic`, `--derivation-path` and `--fund-accounts` at startup; Hardhat's simulated network takes `accounts: {mnemonic, path, initialIndex, count, accountsBalance}` or a list of `{privateKey, balance}` (Hardhat 3 configuration reference, read 2026-11-20; anvil's flags from `anvil --help` as published on getfoundry.sh the same day); both build block 0 from them and change no balance afterwards, and a loaded state wins over them. webevm already has the same mechanism, `createNode({initialBalances})`, applied to a new genesis only. So `createDevNode({...nodeOptions, accounts, balance, fundAccounts})` derives the accounts, merges their balances (and `fundAccounts`, a map of extra addresses to balances, anvil's `--fund-accounts`) into `initialBalances` and creates the node itself, then wraps it; `wrapDevNode` on an existing node funds nothing. For a node created elsewhere (a `createWorkerNode()` whose keys stay on the main thread), `devAccountBalances(options)` returns the same `initialBalances` to pass at creation. Rejected: topping accounts up with `evm_setBalance` after wrapping, which would rewrite state on a chain restored by `loadState` or persistence, and is a cheat where a genesis allocation is the honest form.
- **Inside a worker, through an optional NODE FACTORY on `webevm/worker-host`.** `exposeNode({createEngine, createNode})`: when given, the worker calls `createNode(options)` (with the engine already merged in) instead of webevm's own `createNode`, and exposes what it returns. `@webevm/devnode/worker-host` ships `exposeDevNode({createEngine, accounts, ...})`, which passes `options => createDevNode({...options, ...devConfig})`, so the worker's genesis is funded and the keys are written in the worker module and never cross the thread boundary; the main thread keeps using webevm's own `createWorkerNode()`. A factory rather than a post-creation wrap hook, because funding must happen at genesis, before the node exists. Rejected: the package shipping its own worker host and client, which would duplicate the one place the thread-crossing node proxy exists (CONTEXT.md, *worker host*: a single literal `Required<SlimNode>`, so a field added to `SlimNode` is a build error there rather than an `undefined` on a consumer's main thread). As with `createEngine`, a bad factory, key or mnemonic is reported as a VALUE that rejects the main thread's `createWorkerNode()`, never as a module-scope throw that would hang it.
- **`eth_accounts` lists only accounts whose keys the layer holds, never impersonated addresses**, unlike anvil, which lists an address it has impersonated: appending impersonated addresses would shift what index-declared accounts (rocketh's `deployer: 0`) resolve to, and rocketh copes with both behaviours.
- **Dev accounts send by the node's sender mode.** On a `senderMode: 'trusted'` node through `evm_sendRawTransactionAs` with their REAL signature (no ecrecover, and the dump stays replayable anywhere, because ADR 0002's portability caveat applies only to fabricated signatures); on a `'recover'` node through `eth_sendRawTransaction`.
- **Impersonation is opt-in and never returns a signature that is not one.** Off by default; while off, the impersonation methods answer a real `-32601` naming the option. On, it needs a `'trusted'` node (`createDevNode` creates one; `wrapDevNode` refuses any other), and `eth_sendTransaction` from an impersonated address is sent through `evm_sendRawTransactionAs` with a FABRICATED signature whose bytes are unique per sender (a low `s`, an `r` derived from the address), as ADR 0002's caller contract requires. Every SIGNING method refuses an impersonated address, `eth_signTransaction` included. A dev account that is also impersonated sends with its key.

## Consequences

- The core stays execution-only and its `-32601` edges stay; a consumer who never imports `@webevm/devnode` gets exactly today's webevm.
- The core gains one optional option on `exposeNode` (the node factory), additive, and the aliases and snapshots as ordinary core features.
- A layer on the MAIN thread over a worker proxy serves its ports from the main thread, which gives up `serveOn`'s worker-to-worker path; hosting the layer inside the worker keeps it.
- A dev chain's dumps and alloc exports contain the funded dev accounts, as anvil's state dumps do: they are genesis state.
