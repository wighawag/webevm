# console.log is observed, never answered: a declared engine capability and one observation field on the seam

Solidity developers debug with Hardhat's `hardhat/console.sol` and forge-std's `console.sol` / `console2.sol`, which all `STATICCALL` the fixed address `0x000000000000000000636F6e736F6c652e6c6f67` (the ASCII of `console.log`) with ABI-encoded arguments; Hardhat, anvil and `forge test` print those calls, and webevm loses them. We decided that webevm OBSERVES those calls and never answers them: the engine records the input of every call frame into the console address, the node decodes and delivers them, and execution is not changed in any way. Decided with the maintainer on 2026-11-24, from the spec `work/specs/tasked/solidity-console-log.md`; the same request was filed against tevm as evmts/tevm#2057 and answered there differently (evmts/tevm#2096).

## The decisions

- **Observed, never answered.** The console address holds no code on any real chain, so a call to it costs the account access and returns empty data. tevm answers it with a zero-gas custom precompile at that address. Under EIP-2929 precompiles are warm from the start of every transaction, so the first `STATICCALL` to the address costs 100 gas there instead of the 2,600 of a cold account access on a real chain, and every `eth_estimateGas` that covers a logging path comes back different from what the chain will charge. webevm watches call frames instead and leaves the EVM alone: with console logging on, return data, gas, receipts and the state root are byte-identical to a node without it, on both engines, which is also what keeps the conformance battery's gas comparison meaningful. Rejected: the precompile, for exactly that gas difference.
- **The engine reports raw calls; decoding is above the seam, in one place.** The neutral request (read and transaction alike) gains an opt-in naming an address, and the engine then records the input bytes of every call frame whose CODE ADDRESS is that address, in execution order, whatever the frame's outcome (a frame that later reverts, or a transaction that reverts as a whole, is still recorded, as Hardhat and anvil still print it). CALL, STATICCALL, DELEGATECALL and CALLCODE into the address are recorded; CREATE never is; a frame refused before it runs (call depth over 1024, a value the caller cannot afford) is not. Both engines match the same way. Decoding the calldata is never the engine's job, so two engines cannot decode it two ways.
- **The capability is DECLARED by the engine, and `connectEngine` enforces it.** An engine written against the `Engine` interface as it stood before this decision would ignore both the request opt-in and any context field, and a node built on it would come up with console logging on and print nothing, silently. So the refusal cannot be left to the engine: `Engine` gains an optional member by which an engine declares that it records calls, and `connectEngine` refuses an engine that does not declare it when console logging is enabled, at construction, naming the engine id and the missing capability. This is ADR 0006 amendment 2's rule, a capability the node cannot supply is refused at construction, applied to a new capability. Behind the declaration there is a second guard: when the node asked for recording and the result comes back without the field, the request throws instead of delivering nothing. `webevm/revm` declares the capability only when its revm-wasm artifact's outcome format is 5 or higher (revm-wasm's `recordCallsTo` option and its outcome's `recordedCalls`), decided when the engine is built and so checked at connect, never at the first call; until a revm-wasm release carries it, a console-log-enabled node on `webevm/revm` is refused at construction.
- **The seam admits ONE non-receipt field, and it is an observation: `recordedCalls`. This amends ADR 0006.** ADR 0006 shaped `ReadCallResult` as return data, execution gas and failure, and its amendment 1 shaped `TransactionResult` as everything a receipt needs and nothing else. Both gain `recordedCalls`: optional, present exactly when the request asked for it (possibly empty), named after revm-wasm's outcome field and so that it cannot be confused with EVM event `logs`, which ARE receipt data. It is the only field on either result that no receipt and no RPC answer reads, and the type docs say so. Rejected: a general call tracer on the seam; the opt-in records calls to one address, and a tracer, if one is ever wanted, is its own decision.
- **The option is an INJECTED OBJECT from a subpath, not a flag.** `createNode({consoleLog: consoleLog()})`, with `import {consoleLog} from 'webevm/console-log'`, the same idiom as the engine (ADR 0006): the selector table (the union of pinned Hardhat `console.sol` and forge-std `console.sol` / `console2.sol`, plus the legacy `uint` / `int` spellings), the hand-written ABI decoder (the package has no ABI library and gains none for this) and the browser-safe formatter live in that subpath and cost the default entry nothing. Only the seam plumbing, the observation wiring and `onConsoleLog` are in the core graph. The object carries the sink: by default every entry is printed through the host's `console.log` with a prefix, and `consoleLog({onLog})` replaces that. Rejected: `consoleLog: true`, which would put the decoder in every consumer's bundle.
- **In a Worker, console logging is enabled in the worker module, through a host option.** `createWorkerNode({consoleLog})` is typed `never` and refused at runtime with a message, as `engine` is (a function-bearing object cannot be structured-cloned, and comlink would report only a `DataCloneError`). The worker module passes `exposeNode({createConsoleLog: () => consoleLog()})`, shaped like `createEngine` and refused like it (a misuse is reported as a value, with both signals, never as a module-scope throw that would hang the main thread). Its default sink prints to the worker's console; a custom `onLog` runs on the thread that built the node; the main thread gets entries through `onConsoleLog`, which crosses comlink as a proxy exactly as `onNewHead` does.
- **Estimation prints nothing unless asked, and then only its first execution.** viem estimates before nearly every send and `eth_estimateGas`'s search re-executes up to about twenty times, so printing every execution would multiply each transaction's output. `consoleLog({estimateGas: 'first'})` (the option is `estimateGas?: 'none' | 'first'`, default `'none'`) delivers the logs of the search's first probe (the one at the top of the range) tagged `source: 'eth_estimateGas'`; `eth_fillTransaction`, which runs the same search, follows the same setting tagged `source: 'eth_fillTransaction'`. Never every execution.
- **Delivery is the node's, after the engine returns, and never awaited (ADR 0012).** An entry is `{args, message, source}`, `source` one of `'transaction' | 'eth_call' | 'eth_estimateGas' | 'eth_fillTransaction'`, and a `'transaction'` entry also carries `txHash`, `blockNumber`, `blockHash` and `txIndex`; a transaction's source is `'transaction'` whichever path mined it (automine, `mine()`, `evm_mine`, interval mining). Entries of mined transactions are buffered per block and delivered once the block is stored, in transaction order, before the `onNewHead` emit, so an entry never names a block a failed batch never stored; entries of a read are delivered before its result is returned or its revert error is thrown. `onConsoleLog(cb) => unsubscribe` is a `SlimNode` member. The sink and the subscribers are called synchronously and NEVER awaited, and a throw or a rejected promise from one is caught and reported once through `console.error`, so a debugging aid can never fail a transaction; a callback may issue node requests, which queue behind the current one, as an `onNewHead` callback's do (ADR 0012). On a node created without console logging, `onConsoleLog` throws, naming the option. Malformed console calldata (an unknown selector, a short or corrupt payload) is ignored, not thrown.
- **Console logging is an observation of execution, not chain state.** Nothing is persisted, `dumpState` carries no log, and a `loadState` or a reload replays none.

## Consequences

- A node without console logging pays nothing: the engine records only while a request asked it to, and the default engine attaches its `beforeMessage` listener only for such a request.
- The `Engine` interface grows an optional declaration and an optional request field, both additive; a third-party engine that never declares the capability keeps working everywhere except on a console-log-enabled node, where it is refused at construction rather than silently mute.
- `TransactionResult` is no longer "receipt data and nothing else" without exception; it is receipt data plus, when requested, `recordedCalls`. A later proposal to add another non-receipt field should treat this as the one exception, not a precedent.
- Logs are not exposed over RPC (no `hardhat_setLoggingEnabled`, no subscription over `serveOn`); a consumer reaching the node only through a served port does not see them.
- Console logging on `webevm/revm` needs revm-wasm outcome format 5, published as `revm-wasm@0.6.0` on 2026-11-24 (revm-wasm ADR 0007, `recordCallsTo` / `recordedCalls`); moving webevm onto it is task `console-log-on-the-revm-engine`. Until then the revm engine is refused, with its own reason quoted.
